# macOS's alerts and access

Date: 2026-11-22. Status: built, with what is next at the end. An agent (Claude Code) wrote it after the owner asked for more control over macOS's own alerts and the access it asks for. They had three complaints. A company copy kept asking for access that wasn't needed. The "Background Items Added" alerts never went away by themselves. And clicking one opened System Settings on an error. The owner asked for a diagnosis, skills, a fix, a place among the computer's diagnostics (Raphael, DESIGN §4.11) and preferences in the Settings window (an Alerts tab).

**In short.** Every install made macOS announce Irie's lid check again, as a new background item. Its alerts, and Privacy & Security's, are of a kind that stays on screen, which System Settings doesn't let you change. Login Items crashes when its list changes while it opens, which clicking such an alert does. And a build signed ad hoc is a new program to macOS each time, so it forgets every answer and asks again. Now the lid agent runs a launcher that no install replaces, and the style of both kinds of alert is a setting Irie keeps. Raffi looks at all of this, with a fix that asks first. A script gives a copy's builds a signing identity that stays the same.

|---|---|---|
| An install | "“irie” is an item that can run in the background", an alert that stays on screen (four that morning, 2 to 4 minutes after each install) | Nothing: the agent runs `<data>/lid/irie-lid`, which stays the same file; macOS announces the move once |
| Background Items Added and Privacy & Security's notices | Alerts, which stay until you close each one; System Settings › Notifications doesn't list them | Settings › Alerts: as macOS has them, go by themselves (banners) or stay (alerts); the core keeps the choice |

## 1. What was found

On the owner's Mac (macOS 14.1, 23B2073), 2026-11-22:

- **Background items.** `log show` for `com.apple.backgroundtaskmanagement` showed `invalidateLaunchItem: … url=~/Library/LaunchAgents/io.github.irie-hq.irie.lid.plist` and then "Posting advisory notification request: … body='“irie” is an item that can run in the background…'". This happened 2 to 4 minutes after each install of the day (08:15, 08:47, 09:06 and 09:12; the alerts came at 08:17, 08:51, 09:09 and 09:15). BTM keeps the item under "Unknown Developer". Its program was `~/.local/share/irie/bin/irie`, which each install replaces. Signing the command with a stable identity (since 0764881) did not stop it. A public write-up of the same thing (yugabyte/meko #430 and #439) found that BTM looks at the file the job's `ProgramArguments[0]` names, not at what it holds: once that is a new file, it marks the item "not notified" and alerts again.
- **The style.** In `com.apple.ncprefs`, Login Items' sender (`com.apple.BTMNotificationAgent`) and Privacy & Security's (`com.apple.tccd`) both had their flags' alert bit (1<<4) set. Calendar, Reminders and Clock, which macOS also shows as alerts, have the same bit. Each one's bundle in `/System/Library/UserNotifications/Bundles` sets `UNHideSettings`, which keeps it out of System Settings › Notifications, and `UNSettingModalAlertStyle`.
- **Login Items' error.** Clicking an alert at 09:19:48 opened System Settings. Its Login Items extension crashed 0.4 s later (`~/Library/Logs/DiagnosticReports/LoginItems-2026-11-22-092000.ips`: `EXC_BAD_ACCESS` in Swift code called from `-[BTMManager handleUserDataDidChangeNotification:]`), and System Settings logged "View service terminated with error … Code=4097". The click changes the item the extension is reading (its disposition becomes notified) while the extension is still starting.
- **Access.** tccd's records (`AUTHREQ_CTX`, `_SUBJECT`, `_ATTRIBUTION`, `_RESULT`) put every request from a program Irie started under `subject=io.github.irie-hq.irie`: `sh`, `python`, `mdfind`, browsers, Blender, test builds. macOS holds the app that started a process responsible for it, so an agent's tool that reaches for a folder macOS guards asks in Irie's name. On the owner's Mac nothing asked in the window tccd's lines last (about two hours), as Irie.app has Full Disk Access there. A company copy without it, and signed ad hoc, asks again after every build.

## 2. What is built

- **The lid's launcher** (DESIGN §4.12). The agent runs `<data>/lid/<slug>-lid`, a two-line `sh` script that execs the installed `irie lid check`. It is written only when its text changes, so it keeps its inode and its time. `irie setup lid` writes it. A core moves an older agent onto it as it starts (`lid.Refresh`), but only one that runs its own data dir's binary, so a test core never touches the person's. Then it loads the agent again. `irie setup lid --remove` removes the launcher too.
- **Raffi's look at macOS's alerts** (DESIGN §4.11, `internal/raphael/alerts.go`). It covers each sender whose notices stay until closed, unless the person chose that, with the fix *Let them go by themselves*. It reports the background items macOS announced in the last two hours, with why when the item is Irie's own; the Login Items crash reports of the week; Irie.app and the command signed ad hoc; and the access asked for in Irie's name (an answer by User Consent, 2, or Prompt Timeout, 9), by what for and which program. It reads what it needs from one `log show`. A log that doesn't read says nothing of what was asked.
- **The preference** (`[alerts]`: `background`, `privacy` = `""`, `banners` or `alerts`). The core keeps the style, 30 s after it starts and when the setting changes. It changes that one sender's flags in an export of the settings with PlistBuddy, imports it, and restarts `usernoted` and `NotificationCenter`. Before that it keeps a copy of the settings, the last five, in `<state>/ncprefs`. Raffi's fix does the same and saves the choice. A test core does neither (`IRIE_RAPHAEL=off`).
- **Settings › Alerts** in the Mac app. It has the two styles, Open Login Items and Open Full Disk Access, and Raffi's findings about alerts, each fix behind its OK, with Look again.
- **`tools/sign-identity.sh`.** It makes "<Name> local code signing" (RSA 2048, code signing alone, 10 years) in the login keychain, usable by codesign without asking, and sets the identity tools/live.sh signs with. Given a name, it uses an identity you have.
