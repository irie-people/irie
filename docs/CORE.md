# irie-core

Date: 2026-10-31. Status: first step built. Read with [DESIGN.md](DESIGN.md).

irie-core is all of Irie, for any client. One process, `irie core`, owns every agent, all the state and every rule (DESIGN §2.1). A client, such as the Mac app, the terminal sidebar, `irie ctl` or one you write, draws what the core says and passes on what the person does. It keeps no rules of its own. So a new client has every feature on its first day, and a feature added to the core reaches every client at once.

## 1. The parts

| Part | Where | What it is |
|---|---|---|
| The core | `irie core`, in `internal/core` | The one process that drives tmux and runs the agents (DESIGN §2.2). Clients never start it: `irie up` does |
| The contract | The socket API (DESIGN §2.4). For Go, the package `github.com/irie-people/irie/core` in `core/` | NDJSON over one unix socket: the ops, their args and results, the frames of a subscription. In Go: the wire types and op names, `Socket`, `Dial` and `Call` |
| The language | The `input` op. In Go, `core.Read` and `core.Said` | What a person types in a task bar, read the same way in every client (§3) |

The Go package holds no state and starts nothing: the core is what runs. Its wire types are aliases of the core's own, generated by `go generate ./core`; a test fails when the wire gains a type or constant that the package lacks.

## 2. Writing a client

1. **Find the socket.** `core.sock` in Irie's runtime folder: `$XDG_RUNTIME_DIR/irie`, else `$TMPDIR/irie-<uid>`, else `/tmp/irie-<uid>`, and `/tmp/irie-<uid>` whenever the socket's path would pass the 104 bytes macOS allows (DESIGN §5.4). No socket means no core: say that `irie up` starts one.
2. **Say hello.** `hello` gives the core's version, the API version and `features`, the ops it serves. Offer only what the features name, so an older core never sees an op it lacks.
3. **Subscribe and draw.** `subscribe` sends a snapshot, then a frame for each change: `upsert` and `remove` for rows, `header`, `history`, `outside` and `closed` (DESIGN §2.4). Draw the rows in the order they come; the order is the core's (DESIGN §4.1). A client that shows the slot in its own terminal subscribes with `view: "app"`, as the Mac app does ([MAC.md](MAC.md) §2).
4. **Send what is typed to `input`.** As typed, with the session the person had selected, the selected row outside Irie for `:move`, the client's own menus for where and on what a task runs, and any long paste it shows as a label. Show the reply's `text` as it is. A client never reads the words itself.
5. **Send gestures to the ops they name.** A click on a card is `show`; a drag is `reorder`; the buttons and keys are `park`, `unpark`, `freeze`, `thaw`, `priority`, `close`, `reopen`, `undo`, `redo`, `rate` and `move`; an inline rename is `rename`; a message box is `send`; a conversation view is `conversation` (or `subscribe` with `conversation: true`); a settings window is `config` and `theme`; a first-run welcome is `ready`, what the computer still lacks of what Irie needs, and its fix button is `tool` with `ready`, which runs `irie setup` in a session (DESIGN §2.7). A client with no terminal of its own, such as the phone app ([PHONE.md](PHONE.md)), reads what a session's terminal shows with `screen`, whose `options` are the numbered choices of the prompt it waits on you with, and answers it with `keys`. Keys and buttons are the client's own; what they do is the core's.
6. **Rows from another machine.** A row with `host` is a session of another machine's core that this one is paired with (DESIGN §2.8). Its detail already says where it runs, and that its machine isn't answering while `host_down` is set, which a client may also show by dimming the card; send its id back as it is, and the core passes the call on.
7. **Show the arch agents** (DESIGN §4.11), when `hello` lists `arch`. The op `arch` lists them by rank, each with his `name`, `nickname`, `icon` (one or two emoji), `title` and `about` (his work in a few words and in a sentence), whether he is `on`, a one-line `status` of what he does now, his `actions` and his `settings`. Draw them as they come, and know none of them by name: an action is a `label` to show and, when it is used, its `op` called with its `args` as they came, then its `done` line shown; a setting is a `key` of the `config` op with its `value` now, drawn by its `kind` (`bool` a switch, `duration` a text such as `5m`, `number` a number, `lines` a list of one-line texts) and written back with `config`. So a new arch agent reaches every client with no change to any. Read the list again while it shows: the statuses change as the person works.
8. **Show a terminal**, if the client has one and runs on the same machine: `attach-info` gives the tmux binary, the socket and the session to attach to, and `tmux -S <socket> attach-session -t <session>` shows the slot.
9. **Show errors as they are.** A failed request replies `{"ok":false,"error":{"code":…,"msg":…}}`. The message is written for the person; the code (`bad_args`, `not_found`, `busy` and the rest) is for the client to act on.
10. **Answer the freeze dog**, if the client is a window, when `hello` lists `watch`. On a connection of its own, `subscribe` with `view: "watch"`, the window's `pid` and, for an app, its `bundle`, and answer each `{"t":"ping","ping":N}` from the main loop with `{"pong":N,"front":…,"hidden":…}` on the same connection. A ping left unanswered for `ui.freeze_dog` has the core force quit the window and open the bundle again as it stood (DESIGN §2.4). The Mac app does it in `FreezeDog.swift`, on a thread of its own, so that only a stuck main thread holds an answer up.

In Go:

```go
sock, err := core.Socket()
if err != nil {
	return err
}
var r core.InputResult
err = core.Call(sock, 2*time.Second, core.OpInput, core.InputArgs{Text: "hows the parser?"}, &r)
if err != nil {
	return err // an *core.Error, whose message is the person's to read
}
fmt.Println(r.Text)
```

From a shell, `irie ctl input "hows the parser?"` does the same.

## 3. The language

`input` takes `text`, as typed, and does what it says. Only its first line is read for words; the rest of the text is the task's, as it is.

| Typed | What the core does | `did` |
|---|---|---|
| A task, with `@repo`, `@repo!`, `@path`, `+profile` among its first line's words (DESIGN §4.2) | `spawn`. With no `@` word it runs where `repo` and `in_place` say, the client's menu; with no `+` word on `profile`; on `model` when the client sends one. It is a jot: one that reads as more for the task typed just before ("also …", "it's …", a link) goes to that task's agent instead (DESIGN §4.2, "More for the last jot"), and the same text sent with `apart` naming that session takes it back and starts it apart | `spawned`, with `session`; or `added`, with the `session` it went to and `until` |
| `hows X?`, `how's X going`, `how is X doing` | Answers in one line, from the row whose name, branch, repo, agent, profile or helper best matches every word | `answered` |
| `:rename NAME`, `:rate good\|bad`, `:close`, `:prio [REASON]`, `:park`, `:unpark`, `:freeze`, `:thaw` | The op of the same name on the selected session (`session`); `:prio` promotes it, or puts a promoted one back | `ran` |
| `:freeze all`, `:thaw all` | Every session | `ran` |
| `:reopen`, `:undo`, `:redo` | The session closed last; the history's next step. Nothing to undo is an answer, not an error | `ran`, or `asked` |
| `:move [NAME]` | Brings in the session outside Irie by its id or name, else the selected one (`outside`) | `ran`, with `session` |
| `:route TASK` | Says where `+auto` would run the task, and why | `answered` |
| `:setup [local]`, `:models` | Starts a tool session, which waits on its user | `ran`, with `session` and `show` |
| `:setup switch` | Starts the dead man's switch guide: a Claude Code session on `+claude` with Irie's skill `/irie:dead-mans-switch` ([extensions.md](proposals/extensions.md) §2.2) | `ran`, with `session` and `show` |
| `:vpn`, `:vpn time` | Says Mullvad VPN's state, or the account's time left, while `vpn.on` | `answered` |
| `:vpn on`, `:vpn off`, `:vpn lockdown on\|off`, `:vpn PLACE` | The `vpn` op: connects, disconnects, sets lockdown mode, or goes through another country, city or server. Refused when the words come from inside an agent: the core reads the caller's process from the socket (`LOCAL_PEERPID`, `SO_PEERCRED`) and looks for an agent's host among its parents | `ran` |

Every op runs through the core's dispatch as if the client had sent it, so a typed `:park` is a park in every way: its checks, its journal and its step of the history. What the words can't do comes back as an error in plain words, such as `:park takes the selected session, which must be not parked.`, and nothing runs.

The reply:

| Field | Meaning |
|---|---|
| `did` | `spawned`, `added`, `answered`, `ran` or `asked` |
| `op` | The op it ran, such as `spawn`, `park` or `undo`; none for a question it answered |
| `text` | What to tell the person, as it is |
| `session` | The session it started or acted on. A client selects it; after a `spawned`, the Mac app shows it only when nothing else is on show |
| `show` | Show `session` and give it the keyboard |
| `choice` | When `asked`: the core's question, with its options, the recommended one first. Answer through `op` (`undo` or `redo`) with `choice_id` and the option's `key` (DESIGN §4.5) |
| `until` | When `added`: when the task is typed to the agent. Until then, the same input with `apart` set to `session` takes it back and starts it on its own; a client may offer that as a button |

A long paste the client shows as a label goes in `pastes`, each `{label, text}`. The core reads the words around the labels first, then puts each paste back whole in its place, so a paste's own `@` and `+` words stay text.

## 4. What clients still keep

The language was the largest rule that every client kept a copy of, and the copies had started to differ: the Mac app knew no `:` command, and its question reader dropped a capital "The" that the sidebar kept. These rules are still in the clients, each in two copies, and go to the core next, in this order:

| Rule | In the clients now | Next |
|---|---|---|
| What a row's state is called, its mark and its colour role (DESIGN §5.3) | `States.swift`; `stateLabel` and the marks in `internal/ui` | Each row carries its words, mark and role; a client maps the role to its palette |
| How a history step reads: the core's `park "api-fix"` as Park “api-fix” | `UndoText.title` in `Undo.swift`, for the Edit menu; the core's `Title` already words `input`'s replies so | The `history` frame carries the words, from `Title` |
| Which group a row is in, and a repo's name in the tree | `Store.groupID` and `Store.names`; `groupOf` and `repoNames` in `internal/ui` | Each row carries its group |
| Token counts in short (48.2k) | `Tokens.short` in `Wire.swift`; `internal/ui` | Each row carries the words |
| An agent's own colour, and the palettes | `Theme.swift`; `internal/ui`, which the core imports for the status line's colour | A palette package of the core's, so the core no longer imports a client |
| The wire types, for clients in other languages | `Wire.swift`, by hand | A schema generated from the Go types, and a test that `Wire.swift` decodes only keys the schema has |

The socket's place is part of the contract (§2), so a client may keep its own copy of that rule.

## 5. Checks

- `core/wire_test.go`: the Go contract covers every type and constant of the wire, and every function a client needs.
- `core/read_test.go`, `core/task_test.go`, `core/hows_test.go`: the language, without tmux, in milliseconds.
- `internal/core/input_test.go`: typed words run through the same ops a client sends, and take their step in the history.
- `internal/ui`: the sidebar sends what was typed as it is, with its selection and pastes, and shows what the core says.
